# Make CLI dependency resolution and clean installs reproducible

Ensure the project declares the packages it imports directly and resolves a supported CLI framework combination in fresh environments. Current broad dependency constraints and obsolete extras can produce warnings, omit required runtime packages, or allow framework upgrades that change command introspection, help rendering, and test behavior. A lockfile alone is not sufficient because package consumers resolve from project metadata.

This work establishes a reliable installation baseline for subsequent safety and command-surface changes.

## Design

Review runtime imports, extras, lower bounds, and upper-bound/compatibility strategy rather than applying a one-off lockfile patch. In particular, avoid unsupported extras, declare directly imported runtime packages directly, and decide how framework compatibility will be tested. Regenerate the lockfile using the repository-standard workflow.

Add a clean-install smoke test that exercises the built artifact or an isolated environment rather than relying only on the existing development environment. Keep feature work out of this ticket.

## Acceptance Criteria

- [ ] Every directly imported runtime package is declared as a direct runtime dependency.
- [ ] No unsupported dependency extra is requested and a fresh install emits no related warning.
- [ ] Dependency constraints resolve to a supported Typer/Click combination under the project’s Python versions.
- [ ] The lockfile is regenerated and consistent with project metadata.
- [ ] A clean environment can install the built wheel and run `monarch --help` and `monarch --version`.
- [ ] CLI tests cover framework-sensitive behavior such as nested command registration, help rendering, and option handling.
- [ ] CI and `make verify` pass without manually installing undeclared packages.
