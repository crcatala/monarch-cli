# Add disposable-fixture live mutation contract suite

Provide separately gated live contract coverage for mutation workflows without risking ordinary household data. Read-only live smoke coverage remains owned by mc-vcbk; this ticket owns a narrow fixture lifecycle, mutation assertion, and cleanup/recovery contract.

## Design

Build on mc-3437 without creating a second general live-test runner. Mutation tests use the dedicated `live_mutation` pytest marker and require `MONARCH_LIVE_MUTATION_TESTS=1`; `MONARCH_LIVE_TESTS` must never select them. Each CLI mutation invocation also supplies the ordinary per-invocation `--allow-mutations` authorization established by mc-k48z. The caller must provide an expected test-household identifier, and suite setup must compare it with a read-only lookup before any mutation. A missing or mismatched identifier is a prerequisite failure.

The initial matrix is intentionally limited to a transaction-notes round trip:

1. create a uniquely named zero-balance manual account;
2. create a uniquely marked manual transaction under that account, referencing an existing category read-only when the upstream create contract requires one;
3. update only that transaction's notes through the installed CLI;
4. verify the normalized mutation outcome and bounded transaction-detail readback;
5. delete the transaction and manual account.

The suite may mutate only the account and transaction created for that run. Existing categories or other records may be referenced read-only when required, but must never be edited, deleted, or selected as mutation targets. Split, ownership, review-state, tag, attachment, receipt, batch, refresh, and other mutation coverage is outside the initial matrix and requires a later explicit reviewed matrix addition. In particular, split coverage from mc-hp7w is deferred until this base lifecycle is proven safe and a split-specific disposable fixture is reviewed.

Because public CLI create/delete workflows do not currently exist, fixture setup and teardown may use test-only adapter helpers. Those helpers must still use explicit fixture operation descriptors and the shared authorization, no-unsafe-retry, ambiguity, and mutation-outcome machinery; they must not call upstream mutation methods through the generic read executor or bypass policy because they are test code. They are not registered as public commands.

Generate a high-entropy run ID before the first mutation and include it in every searchable fixture name/note. Record intended and observed effects in a restricted-permission, git-ignored local recovery manifest before and after every mutation attempt. The manifest contains only the minimum operation, run marker, remote IDs, status, and recovery steps needed for cleanup; it excludes credentials, financial values, raw payloads, and unrelated household data.

Cleanup is itself ambiguity-sensitive. It runs after success and definite failure where safe, but a timed-out or disconnected create/delete is never blindly retried. If fixture creation may have succeeded without returning an ID, recovery uses the unique marker for a bounded read-only lookup and requires manual action when identity is not certain. Cleanup failures preserve the manifest and surface a sanitized non-success result with sufficient fixture identifiers and instructions for manual recovery.

## Key Decisions

- **One narrowly proven matrix first.** Initial coverage is transaction-note update on a suite-created manual transaction; broader mutation coverage is not implicit.
- **Two independent authorization layers.** The dedicated live-mutation gate approves the test context, while `--allow-mutations` authorizes each CLI mutation invocation.
- **Fixture helpers do not bypass production safety.** Test-only create/delete helpers use the shared mutation executor and explicit operation metadata.
- **Read-only references are permitted, mutation targets are not.** An existing category may be referenced to create a transaction but is never modified.
- **Recovery is journaled before mutation.** Unique markers and a local manifest support recovery when a response or cleanup is ambiguous.
- **No blind cleanup.** Cleanup follows the same conservative retry and ambiguity rules as every other mutation.

## Acceptance Criteria

- [ ] Mutation live tests use the `live_mutation` marker, require `MONARCH_LIVE_MUTATION_TESTS=1`, and are excluded from normal CI, `make test`, the read-only release check, and `MONARCH_LIVE_TESTS=1` selection.
- [ ] The suite refuses to mutate unless the dedicated opt-in is present, the supplied expected household identifier matches a read-only lookup, and each installed-CLI mutation includes `--allow-mutations`.
- [ ] The initial matrix creates a uniquely named manual account and uniquely marked transaction, updates only that transaction's notes through the installed CLI, verifies it through bounded detail readback, and deletes the created transaction and account.
- [ ] Existing household records are never mutation targets; an existing category may be referenced read-only only when required for fixture creation.
- [ ] Fixture setup and teardown use test-only adapter helpers with explicit operation descriptors and the shared authorization, retry/ambiguity, deterministic non-interactive, and `mutation-outcome.v1` policies rather than direct unguarded upstream calls.
- [ ] A high-entropy run marker and restricted-permission git-ignored recovery manifest are created before the first mutation and updated around every attempted fixture effect.
- [ ] The recovery manifest excludes credentials, raw payloads, financial values, and unrelated household data while retaining the minimum fixture IDs, operation states, and recovery instructions.
- [ ] Cleanup runs after success and definite failure where safe; timeout, disconnect, or cancellation never causes an unsafe automatic retry or blind cleanup.
- [ ] Ambiguous creation without a returned ID uses only a bounded marker lookup; uncertain identity or cleanup failure produces a sanitized non-success result and preserves actionable manual-recovery information.
- [ ] Tests cover gate isolation, missing/mismatched household approval, policy enforcement, setup failure, update success/failure/ambiguity, readback mismatch, cleanup success/failure/ambiguity, and manifest redaction.
- [ ] Split, ownership, review-state, tag, attachment, receipt, batch, refresh, and other mutation workflows are absent from the initial matrix and require an explicit reviewed addition rather than automatic collection.
- [ ] Request limits, timeouts, throttling, expected runtime, residual risks, local execution, cleanup, and manual recovery are documented, and repository verification passes.
