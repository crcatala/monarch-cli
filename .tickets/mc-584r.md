# Add disposable-fixture live mutation contract suite

Provide separately gated live contract coverage for mutation workflows without risking ordinary household data. Read-only live smoke coverage remains owned by mc-vcbk; this ticket owns a narrow fixture lifecycle, mutation assertion, and cleanup/recovery contract.

## Design

Build on mc-3437 without creating a second general live-test runner. Read-only live tests retain the `live` marker. Mutation tests carry both `live` and the dedicated `live_mutation` marker so the normal `-m "not live"` suite excludes them. `make test-live` must select `-m "live and not live_mutation"`, while a new `make test-live-mutation` target selects only `-m live_mutation`. Mutation tests additionally require `MONARCH_LIVE_MUTATION_TESTS=1`. A collection guard deselects `live_mutation` nodes unless that dedicated opt-in is present, and a runtime prerequisite guard independently fails closed before fixture setup. Environment gating is defense in depth and is not a substitute for the supported targets' marker-level isolation; `MONARCH_LIVE_TESTS` alone never enables mutation collection or execution.

Each CLI mutation invocation also supplies the ordinary per-invocation `--allow-mutations` authorization established by mc-k48z. The caller must set `MONARCH_LIVE_MUTATION_HOUSEHOLD_ID` to the exact opaque ID of the approved test household. Before any mutation, a test-only adapter helper performs a minimal read-only query selecting only `myHousehold { id }` and compares the returned ID exactly with the supplied value. Missing, empty, malformed, or mismatched values fail closed. The suite must not derive context identity from names, member lists, accounts, or other mutable records, and must not call `get_credit_history()` merely to obtain the household ID.

The initial matrix is intentionally limited to a transaction-notes round trip:

1. create a uniquely named zero-balance manual account;
2. create a uniquely marked manual transaction under that account, referencing an existing category read-only when the upstream create contract requires one;
3. update only that transaction's notes through the installed CLI;
4. verify the normalized mutation outcome and bounded transaction-detail readback;
5. delete the transaction and manual account.

The suite may mutate only the account and transaction created for that run. Existing categories or other records may be referenced read-only when required, but must never be edited, deleted, or selected as mutation targets. Split, ownership, review-state, tag, attachment, receipt, batch, refresh, and other mutation coverage is outside the initial matrix and requires a later explicit reviewed matrix addition. In particular, split coverage from mc-hp7w is deferred until this base lifecycle is proven safe and a split-specific disposable fixture is reviewed.

Because public CLI create/delete workflows do not currently exist, fixture setup and teardown may use test-only adapter helpers. Those helpers must still use explicit fixture operation descriptors and the shared authorization, no-unsafe-retry, ambiguity, and mutation-outcome machinery; they must not call upstream mutation methods through the generic read executor or bypass policy because they are test code. They are not registered as public commands.

Generate a high-entropy run ID before the first mutation and include it in every searchable fixture name/note. Record intended and observed effects in a restricted-permission, git-ignored local recovery manifest before and after every mutation attempt. The manifest contains only the minimum operation, run marker, remote IDs, status, and recovery steps needed for cleanup; it excludes credentials, financial values, raw payloads, and unrelated household data.

Cleanup is itself ambiguity-sensitive. It runs after success and definite failure where safe, but a timed-out or disconnected create/delete is never blindly retried. If fixture creation may have succeeded without returning an ID, recovery uses the unique marker for a bounded read-only lookup and requires manual action when identity is not certain. Cleanup failures preserve the manifest and surface a sanitized non-success result with sufficient fixture identifiers and instructions for manual recovery.

## Key Decisions

- **One narrowly proven matrix first.** Initial coverage is transaction-note update on a suite-created manual transaction; broader mutation coverage is not implicit.
- **Selectors isolate collection, environment gates execution.** Mutation tests carry `live` plus `live_mutation`; exact marker expressions keep normal and read-only targets from collecting them, while environment checks add defense in depth.
- **Authoritative household identity is explicit.** `MONARCH_LIVE_MUTATION_HOUSEHOLD_ID` must exactly match a minimal server-side `myHousehold.id` lookup before mutation.
- **Two independent authorization layers.** The dedicated live-mutation gate approves the test context, while `--allow-mutations` authorizes each CLI mutation invocation.
- **Fixture helpers do not bypass production safety.** Test-only identity/create/delete helpers remain in the adapter boundary; mutation helpers use the shared executor and explicit operation metadata.
- **Read-only references are permitted, mutation targets are not.** An existing category may be referenced to create a transaction but is never modified.
- **Recovery is journaled before mutation.** Unique markers and a local manifest support recovery when a response or cleanup is ambiguous.
- **No blind cleanup.** Cleanup follows the same conservative retry and ambiguity rules as every other mutation.

## Acceptance Criteria

- [ ] Read-only live tests use `live`; mutation tests use both `live` and `live_mutation`; both markers are registered with pytest.
- [ ] `make test` selects `-m "not live"`, `make test-live` selects `-m "live and not live_mutation"`, and `make test-live-mutation` selects `-m live_mutation`; collection tests prove these supported node sets are disjoint and mutation tests are absent from normal/read-only collection.
- [ ] A collection guard deselects `live_mutation` nodes unless `MONARCH_LIVE_MUTATION_TESTS=1` is present, and an independent runtime guard fails closed before fixture setup; `MONARCH_LIVE_TESTS` alone enables neither mutation collection nor execution.
- [ ] Before mutation, `MONARCH_LIVE_MUTATION_HOUSEHOLD_ID` must exactly match a minimal read-only `myHousehold { id }` adapter lookup; missing, empty, malformed, or mismatched input/response fails closed.
- [ ] Household verification fetches no member, account, credit, profile, or third-party fields and never derives identity from names or mutable records or calls `get_credit_history()`.
- [ ] The suite refuses to mutate unless marker selection, dedicated execution opt-in, household-ID verification, and each installed-CLI mutation's `--allow-mutations` authorization all succeed.
- [ ] The initial matrix creates a uniquely named manual account and uniquely marked transaction, updates only that transaction's notes through the installed CLI, verifies it through bounded detail readback, and deletes the created transaction and account.
- [ ] Existing household records are never mutation targets; an existing category may be referenced read-only only when required for fixture creation.
- [ ] Fixture setup and teardown use test-only adapter helpers with explicit operation descriptors and the shared authorization, retry/ambiguity, deterministic non-interactive, and `mutation-outcome.v1` policies rather than direct unguarded upstream calls.
- [ ] A high-entropy run marker and restricted-permission git-ignored recovery manifest are created before the first mutation and updated around every attempted fixture effect.
- [ ] The recovery manifest excludes credentials, raw payloads, financial values, and unrelated household data while retaining the minimum fixture IDs, operation states, and recovery instructions.
- [ ] Cleanup runs after success and definite failure where safe; timeout, disconnect, or cancellation never causes an unsafe automatic retry or blind cleanup.
- [ ] Ambiguous creation without a returned ID uses only a bounded marker lookup; uncertain identity or cleanup failure produces a sanitized non-success result and preserves actionable manual-recovery information.
- [ ] Tests cover exact marker collection sets, environment-gate defense in depth, missing/empty/malformed/mismatched household approval, minimal identity-query fields, policy enforcement, setup failure, update success/failure/ambiguity, readback mismatch, cleanup success/failure/ambiguity, and manifest redaction.
- [ ] Split, ownership, review-state, tag, attachment, receipt, batch, refresh, and other mutation workflows are absent from the initial matrix and require an explicit reviewed addition rather than automatic collection.
- [ ] Request limits, timeouts, throttling, expected runtime, residual risks, local execution, cleanup, and manual recovery are documented, and repository verification passes.

Owner-approved implementation design refinement (pre-implementation):

1. Recovery manifest location and durability
- Use the repository-relative directory `.monarch-live-mutation-recovery/` (resolved from pytest's repository root), not `tests/live`, `.pytest_cache`, or a temporary directory.
- Add the exact root-anchored entry `/.monarch-live-mutation-recovery/` to `.gitignore`.
- Create the directory with mode `0700` and each per-run JSON manifest with mode `0600`; update manifests atomically using a same-directory temporary file, flush/fsync, and replace.
- Name manifests by the high-entropy run ID. Print the absolute path in any cleanup/recovery failure without exposing credentials, financial values, raw payloads, household IDs, or unrelated records.
- A manifest may be removed only after both fixture transaction and fixture account cleanup are definitively known to have succeeded. Preserve it for every ambiguous, incomplete, interrupted, or failed cleanup outcome. Do not store recovery state in disposable pytest/temp caches.

2. Explicit test-fixture mutation outcomes
- Register four explicit, stable non-public fixture operation mappings in the centralized mutation-outcome registry: `live-fixture.account.create`, `live-fixture.transaction.create`, `live-fixture.transaction.delete`, and `live-fixture.account.delete` (with matching explicit `Operation` descriptors).
- These entries identify real remote effects used only by the live test adapter; they must not be registered as public CLI commands.
- Fixture helpers must use the existing shared authorization, single-attempt/no-unsafe-retry executor, ambiguity classification, sanitized errors, and `mutation-outcome.v1` builder. Do not monkeypatch the registry, introduce a second registry, accept arbitrary outcome IDs, or bypass envelopes for setup/teardown.

3. Installed-CLI boundary
- Provide one shared live-test subprocess runner for both read-only and mutation suites; do not create a second general runner.
- Resolve and invoke the platform-appropriate installed `monarch` console script from the scripts directory of the Python environment running pytest (derived from `sys.executable`). Invoke it directly with `shell=False`.
- Fail closed with setup guidance if that entry point is absent. Do not silently fall back to a bare PATH command, a globally installed CLI, Typer `CliRunner`, or a different environment. `uv run --no-sync monarch` may be documented as a manual fallback, but is not the suite's primary subprocess boundary.
- Only the notes update is performed through the installed public CLI, with the global `--allow-mutations` flag in its required position. Test-only identity/create/delete operations remain adapter helpers governed by the same mutation policies.

Live verification remains an explicit human gate. Before the mutation target is run, the operator must authenticate using the exact resolved local CLI and supply the approved disposable household's exact opaque ID through `MONARCH_LIVE_MUTATION_HOUSEHOLD_ID`. Neither that ID nor authentication material may be persisted in the manifest, progress artifacts, PR, ticket, or test output. Local/mock verification can proceed first, but merge evidence must not represent the live mutation contract as proven until the dedicated gated run succeeds or the owner explicitly records a waiver.
