# Add guarded monthly category budget updates

Add one focused budget mutation for AI-agent and human workflows: set the monthly amount for one category in one explicitly identified month. This closes a useful web/UI parity gap without bundling reset, category-group budgets, flexible budgets, future-month propagation, or rollover settings. The command must use the established mutation authorization, retry/ambiguity, verification, and machine-readable output contracts.

## Design

Add one command:

`budgets set --category-id CATEGORY_ID --amount AMOUNT --start YYYY-MM-DD`

The target is exactly one category and one monthly budget period. `--start` is required, uses the shared strict `YYYY-MM-DD` parser, and must satisfy the documented monthly-period rule (initially the first day of a month). The amount is a finite non-negative currency value with no silent rounding or unit conversion. The command uses the released public `set_budget_amount` capability with `category_id`, the requested amount, `timeframe="month"`, the requested start date, and `apply_to_future=False`; it never sends a category-group target or future-month propagation flag.

Before the write, perform bounded read-only category validation so an unknown category fails before mutation. All local validation and discovery occur before mutation authorization, client creation, or the write attempt. `--dry-run` is a required preview path for agents and performs local validation/discovery only; it never writes a budget. Normal execution requires global `--allow-mutations`, uses the single-attempt mutation executor, and emits `mutation-outcome.v1` with stable operation `budgets.set` and entity `budget`.

After the write, perform bounded budget readback for the exact category/month and verify the observed planned amount against the requested value using the documented currency comparison. A response without a verifiable result, a timeout/disconnect/cancellation, or a readback mismatch is not reported as success and is never retried blindly. The result identifies the category and month and includes requested and observed amounts without exposing raw upstream payloads.

Reset, category-group targeting, flexible-budget updates, flex rollover, `--future` propagation, bulk updates, budget creation/deletion, and budget-rule automation are out of scope. They require separate contracts because their effects and date/rollover semantics differ materially from a single monthly category amount.

## Acceptance Criteria

- [ ] `budgets set` is discoverable and documented with the exact one-category/one-month scope.
- [ ] The command requires `--category-id`, `--amount`, and `--start`; it accepts no positional mutation target and does not expose `--group`, `--future`, flexible-budget, reset, or rollover options in this ticket.
- [ ] Local validation rejects empty category IDs, invalid dates, non-first-of-month dates, non-finite amounts, negative amounts, unsupported combinations, and invalid numeric precision before authentication lookup, mutation authorization, or any write API call.
- [ ] The command performs bounded read-only category discovery/validation before the write; unknown or malformed category records fail closed without a mutation attempt.
- [ ] The command uses the released public budget capability through the adapter/service boundary and sends exactly the intended category target, amount, monthly timeframe, start date, and `apply_to_future=False` semantics.
- [ ] The operation is classified `remote_mutation`, requires global `--allow-mutations`, and uses the shared single-attempt mutation executor rather than the read retry path.
- [ ] `--dry-run` performs local validation and bounded read-only category discovery only, never authenticates for a write, calls the budget mutation endpoint, or claims that remote state changed.
- [ ] The operation uses stable identity `budgets.set`, emits the generic `mutation-outcome.v1` envelope with entity `budget`, and does not introduce a command-specific top-level response shape.
- [ ] After a write attempt, bounded readback selects the exact category/month and verifies the observed planned amount against the requested amount using a documented currency comparison.
- [ ] A successful result contains stable category/month/requested-amount/observed-amount data; raw request bodies, credentials, arbitrary upstream exception text, and unrelated budget payloads are not emitted.
- [ ] A timeout, disconnect, cancellation, malformed response, definitive API rejection, unavailable readback, or readback mismatch is classified through the shared failure/ambiguity policy and is never blindly retried.
- [ ] A category amount of zero is handled deliberately and documented as a valid reset-to-zero amount if the released API supports it; negative values are rejected.
- [ ] No behavior claims to update future months, category groups, flexible budgets, rollover balances, or reset an entire budget; those capabilities remain separate future tickets.
- [ ] Unit and CLI tests cover validation-before-call behavior, category discovery, dry-run isolation, authorization, exact API argument mapping, finite/precision/date handling, zero amount, successful readback, definite failure, transport ambiguity, readback mismatch, output contracts, and command discovery.
- [ ] Existing budget read output, mutation policy, mutation outcome contract, schemas/capability metadata, help guidance, and clean-install verification remain aligned; no live financial API call is required by the default suite.
- [ ] User-facing documentation and repository verification are complete.
