# Migrating to 0.2.0

This guide covers the intentional breaking changes for the `0.2.0` pre-1.0
release. It is written for users upgrading from `0.1.x`, especially scripts
and integrations that invoke mutations or parse CLI output.

## Upgrade checklist

1. Install the new version and run `monarch --help` once.
2. If authentication only uses the legacy pickle session, run
   `monarch auth login` again.
3. Update mutation commands to use `--allow-mutations` and explicit option-based
   targets.
4. Update automation to request JSON explicitly and handle
   `mutation-outcome.v1` results.
5. Review the validation and retry changes below before running writes.

## Authentication and storage

Legacy pickle sessions are no longer read, written, or migrated. If the only
available session is `~/.mm/mm_session.pickle`, authenticate again:

```bash
monarch auth login
```

The CLI never reads or deletes the pickle file. Remove it manually after
confirming the new login works:

```bash
rm ~/.mm/mm_session.pickle
```

The `file-compat` storage backend was removed. Use `keyring`, `file`, or
`MONARCH_TOKEN` instead:

```bash
monarch auth login --storage file
```

## Mutation authorization and syntax

The CLI is read-only by default. Every remote write requires the global
`--allow-mutations` flag **before** the command path. `--yes` only skips a
destructive confirmation; it does not authorize a write.

### Account refresh

```console
# Before
monarch accounts refresh ACC_ID

# After
monarch --allow-mutations accounts refresh --account ACC_ID
```

The `--account` option is repeatable. Omit it to refresh all accounts.

### Transaction updates

Transaction IDs are now explicit options rather than positional arguments:

```console
# Before
monarch transactions update TXN_ID --category CAT_ID

# After
monarch --allow-mutations transactions update \
  --transaction-id TXN_ID \
  --category CAT_ID
```

Use `--dry-run` to preview a supported change. A dry run performs only
read/validation work, does not require `--allow-mutations`, and never prompts:

```bash
monarch transactions update \
  --transaction-id TXN_ID \
  --category CAT_ID \
  --dry-run
```

### Batch updates

Batch IDs are supplied with repeatable `--transaction-id` options or through
`--stdin`; they are deduplicated in first-seen order:

```console
# Before
monarch transactions batch-update TXN1 TXN2 --category CAT_ID

# After
monarch --allow-mutations transactions batch-update \
  --transaction-id TXN1 \
  --transaction-id TXN2 \
  --category CAT_ID
```

### Split input aliases

The legacy split input aliases `--json-input`, `--input-json`, `--file`, and
`--input-file` were removed. Use exactly one of:

```bash
monarch --allow-mutations --yes transactions splits replace \
  --transaction-id TXN_ID \
  --splits-json '[{"merchantName":"Store","amount":-10.00,"categoryId":"CAT_ID"}]'

monarch --allow-mutations --yes transactions splits replace \
  --transaction-id TXN_ID \
  --splits-file ./splits.json
```

Split replacement is a complete-set operation. `transactions splits clear` is
the explicit way to send an empty set.

## Global option placement

Root-level options must come before the command path:

```console
# Before
monarch accounts list --timeout 60

# After
monarch --timeout 60 accounts list
```

This applies when using root-level options such as `--timeout`, `--no-color`,
`--verbose`, `--quiet`, `--json`, `--allow-mutations`, and `--yes`.
Command-local options remain after the command path. Where supported,
`--json` is also available after the command path as a local shortcut.

## Output and automation

For read commands, interactive output is now human-friendly plain text, while
piped or redirected output defaults to JSON. Scripts should request JSON
explicitly instead of relying on TTY detection:

```bash
monarch accounts list --json
# or
monarch --json accounts list
```

Remote mutations and dry-run previews always emit JSON on stdout. `--quiet` and
explicit non-JSON formats are rejected for these operations with
`INVALID_INPUT` (exit code `2`).

After a remote write is attempted, the result uses the shared
[`mutation-outcome.v1`](../mutation-outcomes.md) envelope. In particular:

- `succeeded` exits `0`.
- Definitive `failed` results use the normal nonzero operation/API exit.
- `ambiguous` and `partial` results exit `4` and require verification before
  retrying.
- Remote writes are attempted once; configured automatic retries apply to read
  commands only.

Do not blindly retry a timeout, disconnect, cancellation, or interrupted write.
Follow the verification command in the outcome, or inspect the affected record
with the relevant read command first.

## Validation changes

Inputs that were previously accepted loosely are now rejected before an API
request when possible:

- Dates must use strict `YYYY-MM-DD` syntax.
- `--timeout` must be at least `1`.
- `transactions batch-update --max-concurrency` must be between `1` and `16`.
- Transaction and split amounts must be finite; NaN and infinity are rejected.
- Normalized-only options cannot be combined with `--raw`.
- `--quiet` fails if a returned record has no extractable ID.

## Tag and split behavior

Transaction tag replacement and clearing now use explicit transaction IDs and
repeatable tag IDs or exact, case-sensitive tag names. `transactions tags add`
is a read-modify-write operation that preserves existing tags, but it is not
atomic against concurrent changes.

Split replacement and clearing are guarded complete-set operations. Replacement
input is bounded, must balance to the parent transaction amount, and is read
back after the write for verification. Ambiguous or mismatched writes should be
inspected before retrying.
